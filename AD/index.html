Newsletter Generator · storage architecture

Where newsletter data lives, and every way it moves

The Newsletter Generator is a single self-contained HTML file, opened locally on the marketer's own machine. It has no backend and no server-side storage: every draft lives in the marketer's own browser, and content leaves the browser only as files the marketer chooses to save. This brief describes the data flow end to end. Image bytes are held in an origin-scoped IndexedDB store, kept separate from the small localStorage draft, so large photos do not exhaust the storage quota.

Date: 1 September 2026 Application version: v0.338

No newsletter content ever leaves the browser over the network. The app makes no POST requests, sets no cookies, and sends no telemetry; its only outbound traffic is GET requests that fetch images. Content exits only as files the marketer saves.

System context

One person, one browser, one HTML file opened from disk. There is no web server: the application file is shared locally, and nothing is ever sent to any host.

Data flow and trust boundaries

Three trust zones sit below the marketer's files: the running page (volatile), the browser's origin-scoped stores (persistent, this machine and profile only), and the network (outbound image fetches only).

Network behaviour

The application is opened from a local file and fetches no code over the network. Its code contains exactly one network call: a GET that collects linked images while building the email zip. Beyond that, the browser itself loads any linked image the marketer pastes, the same way any page displays a picture: while editing, in the preview, and when a video card shows its thumbnail. There are no POST requests, no XMLHttpRequest, no WebSocket, no beacon, no cookies and no analytics anywhere in the app.

Storage security properties

Isolation and egress

  • No network egress of newsletter content; the only outbound traffic is image GETs
  • Every store is origin-scoped: readable only by this app, in this browser profile, on this machine
  • The live preview renders inside a script-disabled sandboxed frame
  • The draft is saved synchronously, so it survives an abrupt close

The image locker

  • An origin-scoped IndexedDB database holds the image bytes
  • Same isolation model as the app's folder-memory database
  • Unreferenced bytes are swept on every open, bounding retention
  • If IndexedDB is unavailable, the app stores bytes inline instead and says so visibly

At-rest footprint

  • Image bytes sit in IndexedDB (hundreds of MB), apart from the small draft store
  • Exports re-embed images, so shared files stay self-contained and portable
  • Undo history holds id-tags, not photos, so it stays small

Security preventions already in place

The first group is exercised by the project's own automated dynamic security test (DAST), which attacks the app in a real browser on every build and turns the build red if any payload executes.

Injection and content safety

  • Two-layer injection defence, re-verified on every build: a fast output-escaping check plus a real-browser attack run that pushes hostile payloads through every import door and fails the build if any executes
  • Scheme allow-list at every image render point: only http(s) and image data URIs; script schemes are blocked
  • The live preview renders inside a script-disabled sandboxed frame
  • A baseline content-security-policy ships on the page

Malformed data and file hygiene

  • A corrupt draft file stops with a plain message; the working draft is never replaced
  • Link fields in opened drafts are sanitised on load: script schemes and non-image data URIs are removed
  • Word import writes only a fixed whitelist of text fields; images and markup never import from Word
  • Pasted table text is parsed as plain text; nothing pasted is executed
  • Pasted links are unwrapped from Safelinks wrappers and stripped of tracking parameters
  • The shared application file comes from a controlled, versioned release build
